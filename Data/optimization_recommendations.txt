STRATEGY 1: REDUCE K-VALUE CALCULATION TO INCREASE SELECTIVITY
----------------------------------------------------------------------

Problem: Your K-value (number of root causes to select) is consistently
too high, especially for simple incidents that should have 1 root cause.

Current Behavior Indicates:
- K-value formula likely returns 3 for most incidents
- Insufficient sensitivity to incident complexity
- May be using fixed K or overly generous K calculation

RECOMMENDED ADJUSTMENTS:

A. If Using Fixed K=3:
   → CHANGE TO: Dynamic K based on incident characteristics

   Suggested Formula:
   K = max(1, min(4, floor(0.8 + 0.4 * incident_complexity_score)))

   Where incident_complexity_score considers:
   - Number of affected network elements (normalize to 0-5 scale)
   - Number of distinct fault types in incident
   - Temporal span of alarm sequences
   - Spatial distribution across equipment hierarchy

B. If Using Dynamic K Calculation:
   → REDUCE by 20-30%

   Example adjustments:
   - Current: K = ceiling(log2(num_candidates))
     New:     K = max(1, floor(0.7 * log2(num_candidates)))

   - Current: K = min(5, 2 + num_alarm_types)
     New:     K = max(1, min(4, 1 + floor(0.6 * num_alarm_types)))

C. Implement K-Value Caps Based on Incident Type:

   Simple Incidents (single equipment, single fault type):
   → Force K=1 regardless of other factors

   Moderate Incidents (2-3 equipment, 1-2 fault types):
   → Cap K at 2

   Complex Incidents (4+ equipment or 3+ fault types):
   → Allow K up to 3-4

D. Add K-Value Uncertainty Penalty:

   When selecting K root causes, if the (K+1)-th candidate has
   similar score to the K-th candidate, this indicates uncertainty.

   → REDUCE K by 1 when: score[K+1] / score[K] > 0.85

   This prevents including marginal candidates.

----------------------------------------------------------------------
STRATEGY 2: INCREASE IN-DEGREE THRESHOLD TO FILTER WEAK CANDIDATES
----------------------------------------------------------------------

Problem: Your algorithm includes too many weakly-connected nodes as
root causes, likely due to low in-degree threshold.

Current Behavior Indicates:
- Threshold may be 0 or very low (includes most candidate nodes)
- Insufficient filtering of secondary/derivative fault nodes
- Propagation effects misidentified as root causes

RECOMMENDED ADJUSTMENTS:

A. Increase Absolute In-Degree Threshold:

   Current (estimated): threshold = 0 or 1
   → Recommended: threshold = 2 (require at least 2 incoming edges)

   Rationale: True root causes typically affect multiple downstream
   components. A node with in-degree 0-1 is often a leaf node or
   secondary effect, not a true root cause.

B. Implement Relative In-Degree Filtering:

   Instead of fixed threshold, use percentile-based filtering:

   → Keep only nodes with in-degree >= 75th percentile of all candidates

   This adapts to incident complexity:
   - Simple incidents: Filters more aggressively
   - Complex incidents: Adjusts threshold downward naturally

C. Add In-Degree Variance Check:

   If all candidate nodes have similar in-degree (low variance),
   this suggests unclear causal structure.

   → When variance(in_degrees) < threshold:
      Force K=1 and select only the highest-scored node

   Prevents selecting multiple marginal candidates when evidence
   is ambiguous.

D. Combine In-Degree with Temporal Priority:

   Weight in-degree by temporal ordering:

   adjusted_in_degree = raw_in_degree * (1 + temporal_priority_bonus)

   Where temporal_priority_bonus:
   - +0.3 for earliest alarms in incident
   - +0.1 for early-to-mid alarms
   - 0.0 for late alarms (likely secondary effects)

   This helps distinguish true root causes (early + high in-degree)
   from propagation effects (late + medium in-degree).

----------------------------------------------------------------------
STRATEGY 3: IMPLEMENT SINGLE-ROOT-CAUSE BOOST MECHANISM
----------------------------------------------------------------------

Problem: Only 25.8% single root cause detection vs. 37.4% optimal.
Your algorithm under-identifies clear, simple incidents.

RECOMMENDED ADJUSTMENTS:

A. Add Single-Cause Confidence Detector:

   Before applying standard K-value selection, check if incident
   shows strong single-cause signature:

   Triggers for FORCE K=1:
   ✓ All alarms from single equipment/rack
   ✓ All alarms of same fault type
   ✓ Clear temporal sequence (first alarm >> subsequent alarms)
   ✓ Top candidate score > 2.5x second candidate score
   ✓ Incident affects single network element only

   If ANY 2+ triggers satisfied → Force K=1

B. Score Gap Analysis:

   Calculate ratio between top and second candidate:
   score_ratio = score[1] / score[2]

   → If score_ratio > 2.0: Force K=1 (clear winner)
   → If score_ratio > 1.5: Reduce calculated K by 1
   → If score_ratio < 1.2: Indicates ambiguity, no adjustment

C. Equipment Hierarchy Simplification:

   Count distinct equipment at each hierarchy level:
   - BBU level: X equipment
   - RRU level: Y equipment
   - Interface level: Z interfaces

   → If X=1 and Y=1: Likely single root cause, set K=1
   → If X+Y+Z <= 2: Strong single-cause candidate, cap K at 2

----------------------------------------------------------------------
STRATEGY 4: BREAK THE 3-ROOT-CAUSE ARTIFICIAL CLUSTERING
----------------------------------------------------------------------

Problem: 60.4% of incidents have exactly 3 root causes (unnatural).
Indicates algorithmic bias or threshold effect.

RECOMMENDED ADJUSTMENTS:

A. Check for Hard-Coded K=3 Default:

   Search your codebase for:
   - Default K assignments: K = 3
   - Fallback logic: if (K is invalid) then K = 3
   - Minimum K thresholds: K = max(3, calculated_value)

   → REPLACE all K=3 defaults with K=1

   Rationale: When uncertain, prefer conservatism (K=1) over
   aggressive selection (K=3).

B. Add Randomization/Dithering to Break Threshold Effects:

   If K calculation produces same value for many incidents:

   K_final = K_calculated + random_adjustment

   Where random_adjustment in {-1, 0, +1} based on:
   - Score distribution variance
   - Incident complexity uncertainty
   - Secondary scoring factors

   This creates natural variation in the 1-4 root cause range.

C. Implement Multi-Tier Candidate Scoring:

   Instead of selecting top-K blindly, use tiered selection:

   Tier 1 (must include): Candidates with score > high_threshold
   Tier 2 (maybe include): Candidates with medium_threshold < score < high_threshold
   Tier 3 (exclude): Candidates with score < medium_threshold

   Selection Logic:
   - If Tier 1 has 1 candidate: Return K=1 (only the clear winner)
   - If Tier 1 has 2 candidates: Return K=2
   - If Tier 1 has 0 candidates: Escalate to Tier 2, apply stricter filtering

   This prevents forcing K=3 when only 1-2 strong candidates exist.

----------------------------------------------------------------------
STRATEGY 5: INCREASE 2-ROOT-CAUSE DETECTION
----------------------------------------------------------------------

Problem: Only 7.9% of incidents have 2 root causes (too low).
The algorithm jumps from K=1 directly to K=3, skipping K=2.

RECOMMENDED ADJUSTMENTS:

A. Implement Dual-Cause Pattern Detection:

   Check for common 2-root-cause scenarios:
   ✓ Two distinct equipment units failing simultaneously
   ✓ Two different fault types on same equipment
   ✓ Primary failure + secondary correlated failure
   ✓ AC power failure + DC power failure (dual supply issue)
   ✓ CPRI interface failure + corresponding RRU failure

   When detected → Force K=2

B. Score Clustering Analysis:

   Examine top-5 candidate score distribution:

   If scores show 2-cluster pattern:
   [high, high, ---- gap ----, low, low, low]

   → Set K=2 (two clear winners separated from pack)

   Use clustering algorithm (k-means with k=2) on top-5 scores.

C. Equipment Pairing Logic:

   In telecom hierarchies, common root cause pairs:
   - BBU + corresponding RRU
   - Power supply A + Power supply B (redundancy failure)
   - Primary interface + backup interface

   When paired equipment involved → Bias toward K=2
